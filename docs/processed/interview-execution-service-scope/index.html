  • Q3: Q1 결정에 따라 용량 관리 대상을 외부 AI가 아닌 플랫폼 내부 빌드·배치로 구체화. 결정 수는 그대로 유지.
  • Q4: 사용자가 선택지 3의 지원 범위에 플랜별 제한 조건을 추가. 플랜별 구체적 배정은 후속 BM 결정으로 남기고 이번 인터뷰를 4개로 종료.

3. Q1 인터뷰

  • 외부 에이전트의 작업 시작에 플랫폼이 어디까지 관여합니까?
선택지결정장점단점
1지시를 저장하고 에이전트가 MCP로 확인하여 실행별도 실행 제어 연결 불필요에이전트가 확인해야 작업 시작
2연결된 외부 실행기에 시작·중단 명령 전달웹에서 실행 요청 가능실행기와 명령 전달 체계 필요
3MCP 확인 방식과 실행기 명령 전달 방식 모두 지원실행 환경별 선택 가능두 방식의 상태·실패 처리 필요
  • 추천: 1번. AI를 제공하지 않는 MCP 관제 시스템이라는 설명에 가장 가까운 제안. 꺼져 있는 에이전트는 직접 기동하지 않음.
  • 사용자 원문: 1
  • 결정: 플랫폼이 지시를 저장하고 외부 에이전트가 MCP로 확인하여 실행.

초기 질문과 사용자 정정

  • 초기 제품에서 에이전트를 실제로 실행하는 책임은 어디까지 제공할까요?
선택지결정장점단점
1외부 실행형: 사용자 PC·서버에서 실행, 플랫폼은 지시·상태·결과 관리관제 역할에 집중실행 환경 연결·협조 필요
2플랫폼 실행형: 플랫폼 실행 환경만 지원실행·중단·자원을 직접 관리격리·자격증명·실행 비용 관리 필요
3혼합형: 외부·플랫폼 실행 모두 초기 지원실행 위치 선택두 방식과 장애 처리 구현
  • 초기 추천: 1번. MCP 기반 관제탑을 초기 중심으로 삼는 제안.
  • 사용자 원문: 우리는 AI를 제공하지는 않습니다
  • AI 자체 미제공을 기록. 선택 답변으로 간주하지 않고 실행 제어 책임으로 질문 정정.

4. Q2 인터뷰

  • 독립 서비스는 제시한 8개 묶음으로 확정할까요?
선택지결정장점단점
18개 서비스관련 업무의 변경·저장을 함께 처리묶음 내부 도메인 경계 관리 필요
2계정·인증과 조직·권한을 분리하여 9개인증·조직 관리 독립성 강화권한 판정에 서비스 간 통신 증가
32번에 더해 작업공간과 작업 정의·게시를 분리하여 10개작업 배포·작업공간 관리 독립성 강화활성화·권한·삭제 조정 증가
  • 추천: 1번. 서비스 내부 도메인은 분리하되 밀접한 업무는 같은 서비스에 배치.
  • 사용자 원문: 일단 1번으로 가고 더 추가 될 수 있음 서비스는
  • 결정: 현재 8개 서비스 묶음 채택. 향후 서비스 추가 가능하며 최종 개수를 영구 고정하지 않음.

5. Q3 인터뷰

  • 플랫폼 내부 작업의 처리 용량이 부족하면 어떻게 처리할까요?
선택지결정장점단점
1정해진 대기열 크기·시간 안에서 대기, 초과 시 거절·만료일시 부하 흡수대기 상태·만료 처리 필요
2용량 부족 시 즉시 거절처리·상태 관리 단순사용자가 다시 요청
3작업 종류별 대기 또는 즉시 거절 설정작업 특성별 조절종류별 정책·설정 관리 필요
  • 추천: 1번. 공통 대기 정책을 두고 대기열 크기·최대 대기 시간 조절 가능하게 설계.
  • 사용자 원문: 1 인데 SaaS 이다 보니 리미테이션은 비용 고려해서 걸어 두긴 해야 할 듯
  • 결정: 플랫폼 내부 작업은 제한된 대기열로 처리. SaaS 비용을 고려한 한도 필요. 구체적 수치·플랜 차등·과금은 미정.

6. Q4 인터뷰

  • 어떤 작업을 감사 기록이 반드시 남아야 하는 중요 변경으로 분류할까요?
선택지결정장점단점
1보안·운영 중요 변경: 권한·멤버십·토큰·연결 자격증명·한도 변경, 게시·활성화, 삭제주요 위험 추적·비용 제한일반 편집은 개별 변경 이력으로 추적
2모든 데이터 변경: 문서·메시지·지시 수정 포함넓은 변경 추적저장량·쓰기·보존 비용 증가
3모든 변경과 주요 조회·다운로드접근 추적까지 가능가장 큰 기록량·개인정보 관리 부담
  • 추천: 1번. 감사와 일반 변경 이력을 분리하고 보안 요구에 따라 조회 감사 확장.
  • 사용자 원문: 이건 플랜 따라 다르게 가져가야 할듯 3번까지 되게 하는데 플랜에 따라 제한.
  • 결정: 감사는 모든 변경 및 주요 조회·다운로드까지 지원 가능하게 설계. 제공 범위를 플랜에 따라 제한. 구체적인 플랜별 배정은 미정.
  • 조건부·확장 답변. 전 플랜에 3번을 적용하라는 결정이 아님.

8. 미결정과 적용 한계

  • 개인·팀·엔터프라이즈별 감사 제공 범위와 모든 플랜 공통 필수 감사 기준
  • 감사 수집 자체·사용자 조회·보존·내보내기 중 무엇을 플랜별로 제한할지
  • 조회 감사 저장 실패 시 조회·다운로드 허용 여부: 기존 중요 변경 트랜잭션 정책만으로 추론하지 않음
  • 한도 수치·대기 시간·원가 산정·플랜별 자원 차등·초과 과금
  • 외부 에이전트의 지시 수신·점유·상태 보고·취소 확인 상세 계약
  • 기존 Run/Job 실행 초안 정합화와 정확한 파일별 계약·이전 대응표
  • 이전 7개 인터뷰 결정은 재질문하거나 철회하지 않음.
  • 권한 회수 시 플랫폼 접근 차단과 외부 프로세스 강제 종료는 다름. 외부 에이전트 강제 중단을 보장하지 않음.
  • 감사 플랜 제한이 기존 중요 변경의 로컬 감사 원자적 저장 정책을 자동 폐기하지 않음.
  • 서비스 추가 가능은 새 루트 디렉터리 추가의 포괄 승인이 아님.
  • 이 기록은 명세 승격·제품 코드 변경·테스트·배포 완료를 뜻하지 않음.
